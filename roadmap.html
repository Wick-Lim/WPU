WPU hardware roadmap

Performance is set by memory bandwidth, which is set by the silicon's IO/PHY budget, which is set by the rung and its funding. Only rung ① is near-term buildable; rungs ② and ③ are funding-gated projections, and rung ④ is a further, memory-tech-gated step. Every tok/s figure is an estimate [EST].

The RTL is the same across the ladder — only the memory bandwidth changes (rung ④ re-parameterizes the storage tier, not the compute graph). The FPGA fit and routed Fmax are measured (see Board); there is no running board yet, so every tok/s is modeled until bring-up.

Bandwidth is bound by the chip's IO/PHY budget, which is set by the rung. The datapath is identical throughout; the difference between rungs is the memory system feeding it.

Beyond rung ③ — HBF + HBM (future)

A forward-looking architecture note [EST], not designed or verified — contingent on emerging memory technology. It maps cleanly onto what the RTL already is: a weight-streaming, bandwidth-bound machine (tok/s ≈ BW ÷ 13.87 GB/token). Source: HARDWARE_LADDER.md.

today   NVMe (persist) + DDR/LPDDR (stream BW) → die  ·  KV in DRAM
rung ④   512GB HBF (weights already resident · non-volatile)  —1.6 TB/s→  die  ·  die ⇄ KV in 96GB HBM   (no load / no HBF→HBM path)

Weights → HBF

HBF (High Bandwidth Flash — 3D-NAND stacked HBM-style, announced 2025, not shipping) is non-volatile AND high-bandwidth AND high-capacity. A 512 GB HBF (467 GB weights + ~10% headroom — a tight exact fit; ~1 TB for larger models) at ~1.6 TB/s streams the weights straight to the die — no staging through HBM. One HBF store does both jobs the design splits today: the persistent bulk store (NVMe) and the high-BW stream source (DDR/LPDDR working cache). So: no NVMe tier, no 467 GB DRAM copy, no ~70 s boot-load (weights already resident → instant-on). Flash read latency is hideable for the sequential weight stream (the deep-queue flash_xbar already does this); write endurance is a non-issue (weights are written once, then read-only).

KV → HBM

The MLA latent KV is 87.8 KB/token, accumulating with context → ~90 GB at the full 1M context, so a 96 GB HBM is enough (~6 GB headroom — tight for full 1M, less if capped). It's random-access and latency-sensitive — the one pattern flash latency can't serve, so it lives in low-latency HBM. This is about latency/capacity, not raw tok/s; the speed win comes from the weight-stream BW (HBF): the announced ~1.6 TB/s is per-stack → one stack ~100–115 tok/s [EST]; HBF stacks like HBM, and rung ④ assumes multi-stack by default: 2 stacks (3.2 TB/s) → ~200+ tok/s [EST] (1-stack entry ~100–115) — the cost that comes with the default is the die (~26K MAC lanes, sublinear scaling) and power, which become the binding constraints instead of memory.

Honest caveats. HBF is emerging tech (unshipped). Capped by the same sublinear lane scaling (4× lanes → ~2.40×) — the die must be provisioned to consume the higher BW or compute bottlenecks. Higher power (HBF + HBM run hotter than LPDDR5X — this pulls against the low-power / fanless direction). The RTL fits (flash_xbar is a medium-agnostic address→bytes crossbar; kv_cache_pager/weight_loader already separate KV from the weight stream), so the two-store split is a re-parameterization — but the DDR-tier removal + re-tiering and the vendor HBF/HBM PHY + controllers are not built. All [EST].

Board bring-up
