Synthesizable inference accelerator

The full GLM-5.3-Flash, offline, on a local box.

The target is the published GGUF k-quant of GLM-5.3-Flash (UD-Q4_K_XL, 199.7 GB, a 320.8B-param hybrid MoE, 16.7B active/token) streamed through a Verilog datapath. The Q4_K GEMM core is bit-exact to an independent ggml reference; the model is wrapped by a multi-channel DDR5 + NVMe memory system with formal proofs on the control plane. Single-user, air-gapped: provisioned once with the weights, then run with no network path in or out. The machine was built and proven on GLM-5.2 — what still has to be built for GLM-5.3-Flash is stated immediately below, not buried.

Port status — GLM-5.3-Flash config locked · datapath not complete

GLM-5.3-Flash is not a re-dimensioned GLM-5.2. Its architecture id is glm5next, and 34 of its 45 layers are KDA linear attention — a machine this project has not built. Every dimension below is read from the checkpoint's own GGUF metadata and gated by make glm53f-config-guard; the whole-model top is deliberately un-elaboratable until the three missing pieces land. Everything on this page tagged proven or measured was measured at GLM-5.2 shapes and is inherited as a machine, not as a claim about GLM-5.3-Flash.

Throughput

Every tok/s figure is modeled [EST], not measured on silicon. The amortization mechanism is measured in RTL (the hardware weight-load counter); the accept rate feeding it is a measured model property; the absolute tok/s is their product. The tok/s numbers below are GLM-5.2's. GLM-5.3-Flash's raw denominator is measured from its own tensor map — but the accept rate that divides it is a property of a specific model's draft quality, and for GLM-5.3-Flash it is unmeasured, so no amortized figure for it is published here.

How the number is built

14.118 GB/token — GLM-5.3-Flash, no speculation, measured from its GGUF tensor map
÷ A_eff = ? — the MTP head exists (nextn_predict_layers 1), its accept rate is not yet measured
= not published — quoting one would mean inventing the input
25.50 GB/token — GLM-5.2, no speculation, PE_M=1 (measured mechanism)
÷ A_eff = 1.87 — measured accept rate r₁=0.87
= 13.87 GB/token
→ at 1.54 TB/s → ~111 tok/s [EST]

The composed top glm_q4k_spec_system holds the memory system, the PE_M=K+1 batched verify, and the accept/reject loop at once. Its hardware counter shows ALL-ACCEPT committing exactly K+1 tokens per weight-load (K=3 → 4.00), and the committed stream equals a plain greedy decode.

Rung ladder — set by memory bandwidth

Throughput is bandwidth-bound, and bandwidth is set by the chip’s IO/PHY budget, which is set by the rung.

  • ① Prove-it FPGA ~5–8 tok/s
  • ② Funded custom board ~15–40 tok/s
  • ③ 512GB residency box ≈80 tok/s

Rung-③ design point ≈80 tok/s [measured-inputs EST] — U(K) and the MTP accept rate r are both GLM-5.2 measured; ~95 if GLM-5.2’s deeper MTP hits its published accept depth. For GLM-5.3-Flash the ladder's capacity side eases — 212 GB resident at 1M against GLM-5.2's ~561 GB — and rung ③ splits into two honest builds, because the package count (not the capacity) sets both the bus width and the die's memory PHY: 16 × 16 GB = 256 GB at 1024-bit, ~74 tok/s, or 8 × 32 GB = the same 256 GB at 512-bit — half the PHY, half the speed, ~37 tok/s. Its speed side stays GLM-5.2's until the accept rate is re-measured. See the Roadmap.

How it runs

NVMe/PCIe-bandwidth-bound by design, to keep it cheap: stream MoE experts from the SSD through a DDR working cache into a mostly-idle Q4_K die.

1 TB NVMe ──► flash_xbar ──► DDR working set/cache ──► ddr5_xbar ──► Q4_K compute die ──► token
~199.7 GB weights   N-ch + deep queue   LRU+freq+prefetch   N-ch banked   MLA + DSA + MoE · ggml dequant → fp32 MAC → bf16

The whole memory system is byte-agnostic — it moves addresses, slots, and IDs, never weight bytes. Verification is byte-identical on regression; the controllers add bounded model checking, some lifted to unbounded k-induction. No formal proof touches the numeric datapath — that plane is held by the bit-exact simulation goldens.

Not yet done

Open gaps — most sit at the physical/process boundary that an RTL repo cannot close.

KDA weight streaming + BRAM state

The layer itself is built and gated. What is left is that it must fetch its own nine projections from the GEMV engine instead of being handed them — mechanical, since the engine already accepts Q8_0 on w_type/w_hp/w_q8_d and the loader already emits them. The 4.19 MB/layer recurrent state also has to move from registers to BRAM/DDR, which is a memory decision rather than a plumbing one.

A correction worth recording

This page used to say the KDA wrapper was blocked on shared decoder RTL needing a decision — a Q4_K-only attention slot with no recurrent state. Both facts were true and the conclusion was still wrong: it assumed GLM-5.3-Flash would reuse glm_decoder_block_q4k. It does not. These are siblings, and a sibling declares its own port widths. Nothing shared has to change. The wrong framing was carried for several days; nothing had been built on it, so the cost was direction, not rework.

Decoder layer assembly

Both machines now exist and are gated: glm53f_hc_block (two mHC sites per block) and glm53f_kda_layer (one KDA decode step). Assembly is putting the second inside the first — plus mla_attn_q4k and the MoE/dense FFN for the other 11 blocks — and giving both their real weight streams. No shared RTL change is needed for any of it.

fp32_exp_pipe — the polynomial is now the binding term

With the fp32 sigmoid built, the accuracy of the KDA gates, the o_norm gamma and the mHC softmax is bounded by one thing: a degree-4 Horner exp at 2.3e-4. Worth stating plainly — the fp32 mHC map beats a bf16 one by about 2.4×, not by orders, and no further fp32 plumbing will move that. More terms or a better range reduction would.

Q5_K loader path + llama.cpp seal

The GEMM arm is done; weight_loader_q4k cannot lay out a Q5_K tile yet (packer item) and $fatals rather than streaming Q4_K geometry. The gold-standard gguf_crosscheck against llama.cpp's own dequant is wired but unrun — no checkout available.

fp32_add — fix, or track?

An exactly-rounded adder would make the KDA exact leg bitwise. It also perturbs every pinned netlist baseline in the repo, so it is a decision, not a drive-by. Until made, make fp-ieee tracks the gap.

Whole-runtime GGUF cross-check

The full GGUF run end-to-end and compared against llama.cpp’s runtime argmax. Needs a GPU / large-memory host; no in-repo tool yet.

Vendor PHY IP

DDR5 / NVMe (PCIe) / USB-C PHYs are TB-stubbed. Licensed PHY IP is integrated + signed off at the silicon rung.

Board bring-up

The FPGA fit is measured in-repo; running on a physical dev board needs the board + pin XDC + a MIG bridge.

Fab tapeout & dual-port BIST collar

ASIC tapeout is the rung-③ volume endgame. On-die test: the die already carries an inline clock gate; per-macro BIST collars are memory-compiler-generated in the physical flow.
